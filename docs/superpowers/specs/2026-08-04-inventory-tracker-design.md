# BoxBuddy — Small-Business Inventory Tracker Design

## Overview

BoxBuddy is a mobile-friendly web app (PWA) for tracking small-business inventory. Items can be looked up, added, and edited from any device, with QR-code generation and scanning (including existing manufacturer barcodes/QR codes) for fast lookup. The visual theme uses a set of pre-made cute cat illustrations (calico/orange/grey/white cats in a thick-outline cartoon style, peach/orange/cream palette) already provided in the project root.

## Goals

- Track inventory items with business-relevant fields: cost, price, quantity, reorder threshold, SKU, location, category, notes, photo.
- Generate a printable QR code per item, and support scanning existing product barcodes/QR codes to create or look up items.
- Sync across multiple devices (phone + computer) for a single user/business.
- Simple to build and operate: no user-management system, minimal moving parts.

## Non-Goals (v1)

- Multi-user accounts / per-employee permissions.
- Full offline editing with conflict resolution/sync.
- Native (App Store) app.
- Separate normalized tables for locations/categories (kept as free-text with autocomplete for now).

## Architecture

- **Frontend**: Next.js (App Router), built as an installable PWA (manifest + minimal service worker for the app shell). Mobile-first responsive design.
- **Backend**: Next.js API routes / Server Actions. The browser never talks to Supabase directly — all reads/writes go through the backend, which is the only thing holding Supabase credentials.
- **Database**: Supabase Postgres, single `items` table (schema below).
- **File storage**: Supabase Storage, private `photos` bucket, served via signed URLs generated by the backend.
- **Auth**: Single shared passcode (from an environment variable). Successful login sets a signed, httpOnly session cookie (long-lived, e.g. 90 days). No user table.
- **QR**: Generation server-side via the `qrcode` package (encodes just the short `qr_code` string, not a full URL, so it survives domain changes). Scanning is client-side via `html5-qrcode` (ZXing-based), which also supports common 1D barcodes (UPC/EAN), covering "scan existing product barcodes."
- **Hosting**: Vercel (auto-deploy from git, provides HTTPS required for camera access).

## Data Model

Single `items` table in Postgres:

| field | type | notes |
|---|---|---|
| `id` | uuid, PK | |
| `qr_code` | text, unique | short random code embedded in the generated QR, or a scanned existing barcode/QR value |
| `sku` | text, nullable | user-defined product code, independent of `qr_code` |
| `name` | text, required | |
| `quantity` | integer, default 0 | |
| `reorder_at` | integer, nullable | item is "low stock" when `quantity <= reorder_at` |
| `location` | text | free-text, autocomplete from existing distinct values |
| `category` | text | free-text, autocomplete from existing distinct values |
| `notes` | text, nullable | |
| `cost` | numeric, nullable | cost per unit |
| `price` | numeric, nullable | sale price per unit |
| `photo_url` | text, nullable | path in Supabase Storage |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |

Derived/computed (not stored): margin (`price - cost`), total inventory cost value (`sum(quantity * cost)`), total potential revenue (`sum(quantity * price)`), low-stock list (`quantity <= reorder_at`).

No separate `locations`/`categories` tables in v1 — plain text fields with autocomplete suggestions sourced from `SELECT DISTINCT location/category FROM items`. Can be promoted to real tables later if bulk-rename or hierarchy is needed.

## Screens & Components

- **Login** — passcode field. Success sets session cookie, redirects to Dashboard. Header uses `logo.png`.
- **Dashboard** — summary cards (total items, total cost value, low-stock count), search bar, scrollable item list (thumbnail, name, qty, location). Floating "Scan" and "Add item" buttons.
  - Empty state (no items yet): full-page `greet` illustration + "Add your first item" CTA.
  - No search results: `no results` illustration.
  - Loading state: `loading_searching` illustration.
- **Item detail** — photo, all fields, computed margin, low-stock badge if applicable, "print QR label" button, edit/delete.
- **Add / Edit item form** — all data-model fields, photo capture/upload, category & location autocomplete. Uses `writing` illustration near the form.
- **Scan** — opens camera (`html5-qrcode`). On decode: look up by code → found → item detail; not found → offer "create new item with this code" (manual code entry also available as a fallback if camera access is denied).
- **Settings** — change passcode, About section; uses `random deco` illustration.

Components: `ItemCard`, `ItemForm`, `ItemDetail`, `QrScanner`, `QrPrintLabel`, `SearchBar`, `EmptyState` (parameterized by illustration/message), thin `api/items` route layer (list/create/read/update/delete + `lookup-by-code`).

## QR Code Flow

1. **Generating**: item created without a scanned code → backend assigns a short unique `qr_code` (e.g. `bb_` + random base32) → QR rendered via `qrcode`, shown as a printable label (QR + name + SKU, sized for common label printers).
2. **Adopting an existing code**: scanning an unrecognized barcode/QR offers "create item with this code" — the scanned value is stored directly in `qr_code`, so the manufacturer's label doubles as the item's label.
3. **Looking up**: Scan screen decodes → `GET /api/items/lookup-by-code?code=...` → found → item detail; not found → offer create-new.
4. **Duplicate handling**: `qr_code` is unique in the DB; a collision on create shows "this code is already used by X" rather than overwriting.

## Error Handling & Edge Cases

- No camera / permission denied → manual code-entry fallback, never a dead end.
- Invalid/missing session → 401 → redirect to Login.
- Photo upload failure → inline error, entered form data preserved; 5MB max enforced client-side.
- Offline → PWA app shell (layout, cached illustrations) still loads; live data operations show a clear "you're offline" state. Full offline editing/sync is out of scope for v1.
- Concurrent edits from two devices → last-write-wins via `updated_at` (acceptable at small-business/single-location scale).
- Login rate-limited (e.g. 5 attempts/minute/IP) since the passcode is the only auth gate.

## Testing

- Unit tests (Vitest): QR generation/uniqueness, cost/price/margin math, low-stock threshold logic, autocomplete distinct-value queries.
- API route tests: `items` CRUD + `lookup-by-code`, against a test Supabase schema.
- Manual/browser verification: camera scanning, photo capture, PWA install, and each illustration state (empty/loading/no-results) driven in a real browser before calling any milestone done — these aren't meaningfully unit-testable.

## Deployment

- Supabase project: Postgres `items` table + private `photos` storage bucket. Free tier is sufficient at this scale.
- Vercel project: connected to the git repo, auto-deploys on push, supplies the HTTPS domain needed for camera access.
- Environment variables (set in Vercel, never committed): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (server-only), `APP_PASSCODE`, `SESSION_SECRET`.
- PWA: manifest.json + icons derived from `logo.png` + minimal service worker for the app shell.
- Supabase account/project creation is done by the user (external account signup); implementation can proceed once credentials are shared via environment variables.
